# Changelog

## Unreleased

### Changed
- Claude runs started by the app no longer let the CLI save its own memory notes under `~/.claude/projects/` (outside the workspace, without an approval card). The app sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for the processes it starts; your own use of the CLI is unchanged.
- The backend now checks every 15 seconds for conversation turns (see "Durable local conversations" below) whose process stopped, and interrupts the turns it is running when it shuts down cleanly. It does nothing unless threads are used.
- Boat is now an optional provider. `BOAT_API_KEY`, `HOOK_TOKEN` and `PERMISSION_HOOK_BASE_URL` are no longer required to start the backend; `scripts/dev.sh` only requires the hook settings when a Boat key is set. Work that needs a Boat sandbox answers 503 "Boat is not configured" when the key is empty, and the permission hook endpoint rejects every request when `HOOK_TOKEN` is empty. Existing setups with a key are unchanged. Without a Boat key the app is chat-only unless you enable local tools (below): local Claude answers questions but cannot use schedules, Telegram tasks or GitHub push, so keep Boat configured if you need those.

### Fixed
- docs/SETUP.md no longer says an agent's new instructions and notes apply to its next message in a conversation already started: the Claude CLI keeps a resumed session's system prompt (checked with Claude Code 2.1.302), so they reach conversations started after the change; model and approval mode do apply to the next message. It also says that **Plan only** still lets the CLI save its plan file in `~/.claude/plans`.
- The Approvals panel's **Add a rule** form no longer squeezes the command box to a sliver beside a full-width "Exactly / Starts with" menu; the Decisions and Health filters get the widths they ask for too.
- On SQLite, **Always allow this command** no longer fails with "database is locked" and answers "allowed this once only". Saving (and removing) a rule now takes the write lock before it reads, instead of upgrading a read whose snapshot went stale while the turn the answer had just woken up was writing its events.
- The PostgreSQL schema-equivalence test no longer reports the `agent` table as different: PostgreSQL reports string defaults with a cast (`'ask'::character varying`) and SQLite reports boolean defaults as `1`/`0`; both are now treated as the same default. The agent table and `thread.agent_id` have their own equivalence check.
- The page no longer dead-ends when Claude is not connected in a Boat sandbox. Task history is always readable and expandable (only sending new tasks and replies needs Claude connected; with Boat off the new-task and reply boxes are hidden), and GitHub can be connected as soon as the sandbox exists instead of waiting for the Claude login. With Boat off (`BOAT_API_KEY` empty) the Connect Claude, GitHub and submit steps are replaced by a short explanation, and the history stays visible. New `GET /api/v1/providers` reports whether Boat is on (never a key or URL); an older backend without it is treated as Boat on.

### Added
- Notes for named agents, starter notes, and an agent as one portable file. **Notes:** each agent keeps a Markdown file, `MEMORY.md`, in its own folder (`agents/<id>` under the workspace root, even when the agent works in a project folder). The start of it, at most 200 lines and then 24 KB, is added to every turn after the agent's instructions, marked as background that grants no permission, and the agent is told where the file is so it can keep it current (its edits ask for approval like any other). Anything that looks like a key, token, password or private key is replaced with `[redacted]` when the file is saved and again when it is loaded; the file is written atomically with owner-only permissions, and a link in its place is never followed. `GET /api/v1/agents/{id}/memory` returns the text, its `hash` and how much of it loads; `PUT` saves it, and with `expected_hash` refuses (409 `memory_changed`, with the current text) to overwrite a change the agent made meanwhile. A new `memory_enabled` switch (on by default) keeps the notes out of turns without deleting them. `starter_notes` on `POST /api/v1/agents` gives a new agent its first notes; a duplicate starts with none; deleting an agent deletes its notes. **Export/import:** `GET /api/v1/agents/{id}/export[?include_notes=true]` returns one `.agent.json` file with the name, title, description, instructions and, if asked, the notes; never the model, folder, approval mode, pin or conversations, and the response lists the parts in which something was redacted. `POST /api/v1/agents/import` reads only those fields from such a file (anything else in it is ignored), so an imported agent always starts on `ask` with the default model and its own folder; a name in use gets a number, and `include_notes: false` leaves the file's notes out. **Chat page:** the Agents panel gets Notes (editor with a gauge of what loads, amber from 80% and red once anything is cut, and a choice between the agent's version and yours on a conflict), Duplicate, Pin, Export and Import, and the edit form gets title, description, a notes switch and starter notes. Run `alembic upgrade head`: it adds `agent.memory_enabled` (default true) and changes nothing else. Tested on SQLite and PostgreSQL.
- Approvals in the Chat page, and more of the approvals backend. **Card:** a shell command's card has "Always allow this command" (sends `remember: true`), then Undo; when it cannot be saved the card says it was allowed once only and why. A call a saved rule allowed says so, with "Stop always allowing". The header shows the conversation's approval mode when tools are on. **Approvals panel** (Chat header, and a section of desktop Settings): saved rules for this folder or all (add exact or "starts with", for one folder or every folder; remove), the decision log (newest first, filter by event and conversation, load older, Export CSV) and a health scan. **Backend:** the answer to `remember` returns `rule_id` or `remember_error`; `approval.resolved` carries `by: "saved_rule"` and `rule_id` for an automatic allow; `GET /api/v1/approval-rules?workspace=` lists the rules that apply in a folder; deleting a rule is logged as a new `undone` decision (`?thread_id=` names the conversation); decision entries record the approval `mode`; `GET /api/v1/decisions/export.csv` exports the log (same filters, redacted again, spreadsheet formulas neutralised). **Sentinel:** `GET /api/v1/sentinel/scan?hours=24` and `python -m app.services.sentinel [--hours N] [--json]`, a read-only scan of stored thread events and the decision log for retry loops, repeated denials, tool errors and failed answers; issues hold normalized titles and evidence ids, never tool output. **Safety floor:** `diskutil eraseDisk`/`eraseVolume`/`reformat`/`zeroDisk`, `/dev/disk/by-*` and `/dev/md/*` devices, `/libx32` and `/lib*`, the `function f { f|f& }; f` fork bomb, and commands inside `eval` are now caught; a program named by a variable (`$CMD`, `bash -c "$CMD"`, `eval $X`) is unreadable, so never auto-allowed. Fixed: `rm --no-preserve-root /` without `-r` raised an error in the floor reader instead of being read. No migration.
- Named agents (F06, backend). An agent is a reusable setup: name, optional title and description, instructions, model, workspace and approval mode (`ask`, `accept_edits` or `plan`), and it can be pinned, archived, duplicated or deleted. New endpoints under `/api/v1/agents` (`GET`/`POST`, `GET`/`PATCH`/`DELETE` by id, `POST .../duplicate`), local access only like threads. Start a conversation from one with `agent_id` on `POST /api/v1/threads`: the agent's provider is used and its workspace is pinned for that conversation (an agent with no folder of its own gets `agents/<id>` under the default workspace root), and every message uses the agent's current instructions (added to the CLI's own system prompt), model and approval mode; a model set on the conversation wins over the agent's. Names are unique among live agents. Deleting an agent keeps its conversations, unlinked, and they carry on without its instructions; archive to keep them linked. Run `alembic upgrade head` (`scripts/dev.sh` does): it adds the `agent` table and `thread.agent_id`, and changes nothing that exists. Tested on SQLite.
- Approval modes, saved command rules, a safety floor and a decision log for local Claude turns (backend). **Modes** `ask` (the default and today's behaviour), `accept_edits` (the CLI lets file edits in the workspace through, everything else still asks) and `plan` (read-only) map onto the Claude CLI's own `--permission-mode`; an unknown mode is refused before the CLI starts, and chat-only runs stay locked down. There is deliberately no "full access" mode. **Always allow:** answering an approval with `{"decision": "allow", "remember": true}` saves that exact Bash command as a rule for that conversation's workspace folder; `GET/POST/DELETE /api/v1/approval-rules` list, add (exact or word-prefix match, optionally tied to a folder) and remove rules. A prefix rule never matches a command with shell operators (`;`, `&`, `|`, redirections, backticks, `$(`). Commands containing a credential, control characters or anything on the floor cannot be saved, and at most 200 rules are kept. A matching rule answers the question at once (the approval is still recorded and shown). **Safety floor:** a never-list of commands no rule can allow: recursive delete of `/`, the home folder or a system directory, recursive `chmod`/`chown` of the same, formatting or overwriting a disk device, force pushes, and fork bombs; a command that cannot be read to the end (unbalanced quote, `$(...)`, `eval`) is held too. Such a call is asked about on a card as usual. **Decision log:** every card shown, allow, deny, rule auto-allow, timeout and cancellation is appended, with secrets removed and the input cut to one summary line, to a monthly `decisions-YYYY-MM.ndjson` (mode 0600, in `~/.open-dots/decisions`, `DECISION_LOG_DIR`, or the desktop data folder; months older than `DECISION_LOG_RETENTION_DAYS`, default 180, are deleted). `GET /api/v1/decisions` reads it, newest first, with a `before` cursor and `event` and `thread_id` filters. All of it is local access only. No migration. See [docs/SETUP.md](docs/SETUP.md#approval-modes-saved-rules-and-the-decision-log).
- Chat page: answers are rendered as Markdown (headings, lists, tables, quotes, emphasis, inline code, and fenced code blocks with a Copy button). It is a small built-in parser with no new dependency: raw HTML is never rendered, only `http`, `https` and `mailto` links are clickable, and a half-written streaming answer renders safely. The earlier "Markdown: not yet" note no longer applies.
- Chat page: an Agents panel (list, create, edit, archive; name, instructions, model with suggestions, workspace folder, and an approval mode of Ask first, Accept edits or Plan only with a plain-language description), an agent picker for new chats, and the agent's name in the conversation list and header. It uses `GET/POST /api/v1/agents`, `GET/PATCH/DELETE /api/v1/agents/{id}` and `agent_id` on `POST /api/v1/threads`; against a backend without them (404) the controls are hidden and the page works as before.
- Desktop Settings: database-backed, versioned local Claude preferences with sensitive-change auditing, native file/folder Browse, per-turn apply rules and fail-closed validation. Conversations now pin their workspace; database upgrades back up existing history before adding the workspace and settings schema.
- A desktop app, run from a source checkout (experimental, Windows verified; macOS and Linux not yet run): an Electron window around the local backend, for local Claude only. `npm run app` in `desktop/` does whatever is missing (setup the first time, a build when the page is out of date) and then opens it; or run `npm run setup`, `npm run build`, then `npm run start` (`npm run dev` uses its own data folder); starting never installs or builds. It needs no `.env`: on first start it makes an encryption key and keeps it with the operating system's secret storage (never as plain text, never replaced if it cannot be read), creates its SQLite database in its data folder, copies the database aside before an update that changes it, and leaves the file whole when it stops. Only its own window can use the backend: a fresh random launch token is handed to the backend before it listens and added to every request the window makes, so a browser tab or another program that finds the address gets nothing; the address and port are chosen by the operating system on every start. The Chat page now also says when it is opened outside the app, and has a "Check again" button when Claude is missing or signed out. A new `Open Dots` data folder holds the database, backups, logs and workspace; see [docs/SETUP.md](docs/SETUP.md#desktop-app-from-a-source-checkout-experimental). Source and headless installs read the same settings as before and are not affected.
- Stop, and managing conversations, in the Chat page and the threads API. **Stop** replaces Send while Claude is answering: Claude is stopped, what it had written so far is kept and marked unfinished, a question waiting for your Allow is cancelled (nothing runs), tool steps that had not finished are marked, and the conversation carries on with the same session. `POST /api/v1/threads/{id}/stop`. **Rename, archive and delete** are in each conversation's menu in the list: renaming keeps its place in the list, archiving hides it (and "Show archived" brings it back, with Unarchive), deleting asks first and removes the conversation's messages, tool calls and approvals from this app's database (not a secure erase: see docs/SETUP.md). Archiving and deleting are refused while an answer is running (stop it first). `PATCH /api/v1/threads/{id}` (`title`, `archived`) and `DELETE /api/v1/threads/{id}`. Deleting does not remove Claude's own copy of the session, which the Claude CLI keeps in your `.claude` folder; that is said in the confirmation. See [docs/SETUP.md](docs/SETUP.md#the-chat-page).
- A Chat page at `/chat` (link "Open chat" on the home page), the first interface for durable conversations. A list of conversations on the left; on the right, the conversation with answers appearing as Claude writes them, each tool call as a step you can open to see its exact input and output, and an approval card that shows exactly what will run and waits for Allow or Deny (nothing runs before). Reload the page or restart the backend and the whole conversation is still there, and the next message continues the same Claude session. If the backend stops while Claude is working, the page says so and that the message was not resumed or sent again; if Claude can no longer find a conversation's session, it explains and offers "Start a new session". Not yet: Markdown formatting (answers are plain text). It needs the same setup as Local Claude and shows what to change when it is off or not signed in. See [docs/SETUP.md](docs/SETUP.md#the-chat-page).
- Durable local conversations ("threads", experimental, off by default). A thread keeps its messages, answers, tool calls and approvals in the database, so a conversation survives a page refresh and a backend restart, and each new message continues the same Claude session. New endpoints under `/api/v1/threads`, local access only and behind the same `LOCAL_EXECUTION_ENABLED` switch as local Claude: create and list threads, send a message, page stored events, a server-sent-events stream that a browser can resume with `Last-Event-ID` and receive exactly what it missed, and answer approvals. The Chat page (see the next entry) is its interface; the Local Claude card is unchanged. A turn that was running when the backend stopped is marked interrupted and is never run again. A conversation whose Claude session can no longer be found fails with `session_resume_failed` and must be reset explicitly with `POST /api/v1/threads/{id}/session/reset`; the app never silently starts a fresh session. Transcripts, including what Claude read, wrote and ran, are now stored in the database, and there is no way to set a retention period yet (conversations can be deleted one at a time, see the next entry). Run `alembic upgrade head` after updating (`scripts/dev.sh` does); it adds four tables and changes nothing that exists. Tested on SQLite; on PostgreSQL the migration applies but the behaviour has not been verified yet. See [docs/SETUP.md](docs/SETUP.md#durable-threads-experimental).
- Local Claude can use tools, with your approval (opt-in): set `LOCAL_TOOLS_ENABLED=true`. Claude can then read and write files in its workspace folder and run commands (`Read`, `Write`, `Edit`, `Glob`, `Grep`, `Bash`). The page shows each tool call as a step, and when the Claude CLI would ask a person it shows the exact input with Allow and Deny buttons; nothing runs until you allow it. No answer in `LOCAL_APPROVAL_TIMEOUT_SECONDS` (default 300), Deny, or the run ending is a refusal, and time spent waiting does not count towards `LOCAL_TASK_TIMEOUT_SECONDS`. New endpoints `GET /api/v1/local/tasks/{id}/approvals` and `POST /api/v1/local/tasks/{id}/approvals/{approval_id}` (local access only); `GET /api/v1/local/status` now reports `tools_enabled`. An allowed `Bash` call runs as you with no sandbox, the CLI decides which calls ask, and approvals and the timeline are in memory only; read [SETUP.md](docs/SETUP.md#tools-and-approvals-local-claude) first. Off by default: runs stay chat-only.
- `python -m app.db.copy_to_sqlite`: copies an existing PostgreSQL database into a new SQLite file. PostgreSQL is only read (one read-only snapshot) and never changed; the copy is built under a temporary name, verified row by row (credentials must still decrypt with your `TOKEN_ENCRYPTION_KEYS`), and published without overwriting anything, so a failed copy leaves no file. It refuses while tasks are active or other connections are open (`--allow-active` overrides), supports `--dry-run`, and does not change `DATABASE_BACKEND`: switching to SQLite is a separate step. See [docs/SETUP.md](docs/SETUP.md#moving-existing-data-from-postgresql-to-sqlite).
- Experimental SQLite storage (opt-in, no Docker): set `DATABASE_BACKEND=sqlite`. PostgreSQL remains the default and nothing changes for existing setups. New SQLite files start from a frozen baseline of the current schema; models use dialect-aware types that leave the PostgreSQL schema unchanged. Concurrency was reworked for SQLite (permission-approval wait, conflicting approval answers, reply admission, schedule claiming, no database snapshot held across slow sandbox/CLI calls); PostgreSQL behaviour is unchanged. Keep PostgreSQL for real Boat sandboxes and multi-process setups until those are exercised on SQLite; see [docs/SETUP.md](docs/SETUP.md#database).
- Local Claude answers now stream into the web UI as Claude writes them (server-sent events, `GET /api/v1/local/tasks/{id}/events`). The saved task still decides the final outcome, a partial answer is kept if a run fails, and an empty answer is shown as such. The existing polling endpoints still work. Events live in memory for now (single backend process).
- Local Claude (experimental, off by default): run chat-only prompts through your own signed-in `claude` CLI from the web UI. Only usable from the machine running the backend. See [docs/SETUP.md](docs/SETUP.md#local-claude-experimental).
