# Changelog

## Unreleased

### Changed
- Claude runs started by the app no longer let the CLI save its own memory notes under `~/.claude/projects/` (outside the workspace, without an approval card). The app sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for the processes it starts; your own use of the CLI is unchanged.
- The backend now checks every 15 seconds for conversation turns (see "Durable local conversations" below) whose process stopped, and interrupts the turns it is running when it shuts down cleanly. It does nothing unless threads are used.
- Boat is now an optional provider. `BOAT_API_KEY`, `HOOK_TOKEN` and `PERMISSION_HOOK_BASE_URL` are no longer required to start the backend; `scripts/dev.sh` only requires the hook settings when a Boat key is set. Work that needs a Boat sandbox answers 503 "Boat is not configured" when the key is empty, and the permission hook endpoint rejects every request when `HOOK_TOKEN` is empty. Existing setups with a key are unchanged. Without a Boat key the app is chat-only unless you enable local tools (below): local Claude answers questions but cannot use schedules, Telegram tasks or GitHub push, so keep Boat configured if you need those.

### Fixed
- The page no longer dead-ends when Claude is not connected in a Boat sandbox. Task history is always readable and expandable (only sending new tasks and replies needs Claude connected; with Boat off the new-task and reply boxes are hidden), and GitHub can be connected as soon as the sandbox exists instead of waiting for the Claude login. With Boat off (`BOAT_API_KEY` empty) the Connect Claude, GitHub and submit steps are replaced by a short explanation, and the history stays visible. New `GET /api/v1/providers` reports whether Boat is on (never a key or URL); an older backend without it is treated as Boat on.

### Added
- Stop, and managing conversations, in the Chat page and the threads API. **Stop** replaces Send while Claude is answering: Claude is stopped, what it had written so far is kept and marked unfinished, a question waiting for your Allow is cancelled (nothing runs), tool steps that had not finished are marked, and the conversation carries on with the same session. `POST /api/v1/threads/{id}/stop`. **Rename, archive and delete** are in each conversation's menu in the list: renaming keeps its place in the list, archiving hides it (and "Show archived" brings it back, with Unarchive), deleting asks first and removes the conversation's messages, tool calls and approvals from this app's database (not a secure erase: see docs/SETUP.md). Archiving and deleting are refused while an answer is running (stop it first). `PATCH /api/v1/threads/{id}` (`title`, `archived`) and `DELETE /api/v1/threads/{id}`. Deleting does not remove Claude's own copy of the session, which the Claude CLI keeps in your `.claude` folder; that is said in the confirmation. See [docs/SETUP.md](docs/SETUP.md#the-chat-page).
- A Chat page at `/chat` (link "Open chat" on the home page), the first interface for durable conversations. A list of conversations on the left; on the right, the conversation with answers appearing as Claude writes them, each tool call as a step you can open to see its exact input and output, and an approval card that shows exactly what will run and waits for Allow or Deny (nothing runs before). Reload the page or restart the backend and the whole conversation is still there, and the next message continues the same Claude session. If the backend stops while Claude is working, the page says so and that the message was not resumed or sent again; if Claude can no longer find a conversation's session, it explains and offers "Start a new session". Not yet: Markdown formatting (answers are plain text). It needs the same setup as Local Claude and shows what to change when it is off or not signed in. See [docs/SETUP.md](docs/SETUP.md#the-chat-page).
- Durable local conversations ("threads", experimental, off by default). A thread keeps its messages, answers, tool calls and approvals in the database, so a conversation survives a page refresh and a backend restart, and each new message continues the same Claude session. New endpoints under `/api/v1/threads`, local access only and behind the same `LOCAL_EXECUTION_ENABLED` switch as local Claude: create and list threads, send a message, page stored events, a server-sent-events stream that a browser can resume with `Last-Event-ID` and receive exactly what it missed, and answer approvals. The Chat page (see the next entry) is its interface; the Local Claude card is unchanged. A turn that was running when the backend stopped is marked interrupted and is never run again. A conversation whose Claude session can no longer be found fails with `session_resume_failed` and must be reset explicitly with `POST /api/v1/threads/{id}/session/reset`; the app never silently starts a fresh session. Transcripts, including what Claude read, wrote and ran, are now stored in the database, and there is no way to set a retention period yet (conversations can be deleted one at a time, see the next entry). Run `alembic upgrade head` after updating (`scripts/dev.sh` does); it adds four tables and changes nothing that exists. Tested on SQLite; on PostgreSQL the migration applies but the behaviour has not been verified yet. See [docs/SETUP.md](docs/SETUP.md#durable-threads-experimental).
- Local Claude can use tools, with your approval (opt-in): set `LOCAL_TOOLS_ENABLED=true`. Claude can then read and write files in its workspace folder and run commands (`Read`, `Write`, `Edit`, `Glob`, `Grep`, `Bash`). The page shows each tool call as a step, and when the Claude CLI would ask a person it shows the exact input with Allow and Deny buttons; nothing runs until you allow it. No answer in `LOCAL_APPROVAL_TIMEOUT_SECONDS` (default 300), Deny, or the run ending is a refusal, and time spent waiting does not count towards `LOCAL_TASK_TIMEOUT_SECONDS`. New endpoints `GET /api/v1/local/tasks/{id}/approvals` and `POST /api/v1/local/tasks/{id}/approvals/{approval_id}` (local access only); `GET /api/v1/local/status` now reports `tools_enabled`. An allowed `Bash` call runs as you with no sandbox, the CLI decides which calls ask, and approvals and the timeline are in memory only; read [SETUP.md](docs/SETUP.md#tools-and-approvals-local-claude) first. Off by default: runs stay chat-only.
- `python -m app.db.copy_to_sqlite`: copies an existing PostgreSQL database into a new SQLite file. PostgreSQL is only read (one read-only snapshot) and never changed; the copy is built under a temporary name, verified row by row (credentials must still decrypt with your `TOKEN_ENCRYPTION_KEYS`), and published without overwriting anything, so a failed copy leaves no file. It refuses while tasks are active or other connections are open (`--allow-active` overrides), supports `--dry-run`, and does not change `DATABASE_BACKEND`: switching to SQLite is a separate step. See [docs/SETUP.md](docs/SETUP.md#moving-existing-data-from-postgresql-to-sqlite).
- Experimental SQLite storage (opt-in, no Docker): set `DATABASE_BACKEND=sqlite`. PostgreSQL remains the default and nothing changes for existing setups. New SQLite files start from a frozen baseline of the current schema; models use dialect-aware types that leave the PostgreSQL schema unchanged. Concurrency was reworked for SQLite (permission-approval wait, conflicting approval answers, reply admission, schedule claiming, no database snapshot held across slow sandbox/CLI calls); PostgreSQL behaviour is unchanged. Keep PostgreSQL for real Boat sandboxes and multi-process setups until those are exercised on SQLite; see [docs/SETUP.md](docs/SETUP.md#database).
- Local Claude answers now stream into the web UI as Claude writes them (server-sent events, `GET /api/v1/local/tasks/{id}/events`). The saved task still decides the final outcome, a partial answer is kept if a run fails, and an empty answer is shown as such. The existing polling endpoints still work. Events live in memory for now (single backend process).
- Local Claude (experimental, off by default): run chat-only prompts through your own signed-in `claude` CLI from the web UI. Only usable from the machine running the backend. See [docs/SETUP.md](docs/SETUP.md#local-claude-experimental).
