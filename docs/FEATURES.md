# Features

Shipped capabilities of Open Duet, a workspace for AI coworkers: named agents with instructions, memory, routines, computers and approvals. Planned work is in [ROADMAP.md](ROADMAP.md). The first bullets describe the original Boat-sandbox task flow, which is optional.

- Run Claude Code tasks in disposable Boat sandboxes from Telegram or the web UI.
- Connect Claude through its OAuth login flow; optionally connect GitHub.
- Approval prompts for risky actions (file writes, shell commands, Git pushes) with remembered permission rules and a Git command classifier that distinguishes branch/remote listings from mutations.
- Continue completed tasks in the same Claude conversation from the web UI.
- Schedule recurring prompts with failure tracking; results reported to Telegram-linked users (Boat sandboxes).
- **Routines (no Boat needed):** run a prompt on a local named agent on a cron, weekday, interval or one-off schedule in any timezone, by webhook (`POST /hooks/{id}` with a bearer secret shown once), or by hand. Missed and skipped occurrences are recorded, unattended approvals park the run and time out to a denial, runs cut off by a restart are marked interrupted and never re-run, a failed run can be retried up to three times after a delay (off by default), every run links to its conversation, and an in-app notification feed (optionally copied to one Telegram chat) reports outcomes. See [ROUTINES.md](ROUTINES.md).
- **Everyday use** (see [EVERYDAY.md](EVERYDAY.md)): search every conversation's title and messages from the conversation list (every word must match, highlighted snippets, filters for archived and agent; works on SQLite and PostgreSQL); attach images and text files by pasting, dropping or picking them (stored privately per conversation with type and size limits; text goes into the prompt, images reach Claude as image blocks and are refused clearly by engines that cannot read them; thumbnails in the transcript); a Files panel to browse, preview and download the conversation's workspace (a file, or a folder as a zip of up to 2000 files and 200 MB), confined to it (no `..`, no symlink escapes, secret files such as `.env` and keys never served); tokens and cost per turn as the engine reported them ("not reported" otherwise), a conversation total, and a monthly Usage panel with a CSV export; failed turns say what to do next.
- **Reliability:** one backend per SQLite database (a second one refuses to start), SIGTERM interrupts running turns and routine runs and leaves no engine process behind, a turn watchdog fails an engine that goes silent (`engine_stalled`), and a broken engine never blocks startup or another engine; on PostgreSQL one backend runs the routine scheduler (advisory lock, takeover when it stops); the next start ends engine processes a `kill -9` left running (verified by pid, start time and program); an interrupted turn says whether the engine had the message. See [RELIABILITY.md](RELIABILITY.md).
- **Limits and fallback engine:** usage/rate limits and lack of credits are recognised for every engine (`engine_limited`), the engine shows a "resets in" chip in the picker and in `GET /engines`, and an agent may name a fallback engine that takes a turn its engine refused before starting, only when it can do what the turn needs, with a visible "switched engine" notice. See [ENGINES.md](ENGINES.md#limits-and-the-fallback-engine).
- Encrypted credential storage; sandbox, task, permission and schedule records in PostgreSQL (default), or in a local SQLite file when `DATABASE_BACKEND=sqlite` (experimental; see [SETUP.md](SETUP.md#database)).
- Guest web mode without Telegram, optionally linked to a Telegram identity via link codes; the identity is kept by the server for the signed-in owner, not by the browser.
- **Owner sign-in and paired devices:** one owner passphrase (scrypt-hashed), an `HttpOnly` session cookie with CSRF protection, and **Settings → Devices** to pair a phone or another browser with a one-time code and QR (5 minutes, single use, brute-force lockout), choose full or chat-only access, see last-seen times and revoke. Requests are refused unless their `Host` is in `TRUSTED_HOSTS`; loopback trust is opt-in (`LOOPBACK_TRUST`). The desktop app keeps its launch token. See [AUTH.md](AUTH.md).

- **Local Claude (experimental, off by default):** run a prompt through your own signed-in `claude` CLI on the same machine, from the web UI, with the answer appearing as Claude writes it. Chat-only by default. With `LOCAL_TOOLS_ENABLED=true` Claude can read and write files in its workspace folder and run commands, shown as a timeline, and each call it would ask about waits for your Allow or Deny in the page. Usable from the machine running the backend, or from a signed-in or paired session. See [SETUP.md](SETUP.md#local-claude-experimental).

- **Durable threads and the Chat page (experimental, off by default):** with the same switch as local Claude (`LOCAL_EXECUTION_ENABLED`), conversations are stored in the database. Messages, answers, tool calls and approvals survive a page refresh and a backend restart, and each message continues the same Claude session. A server-sent-events stream shows answers as they are written and resumes exactly after a disconnect. An interrupted turn is marked and never run again; a lost Claude session must be reset explicitly. The Chat page (`/chat`, linked from the home page) shows them: a list of conversations, answers as they are written, tool calls and approvals in order, and a clear message with a way forward when a session is lost. You can stop an answer, and rename, archive or delete a conversation. Answers are formatted as Markdown (code blocks have a Copy button; raw HTML is never rendered). Not yet: search. See [SETUP.md](SETUP.md#the-chat-page).

- **Agents in the Chat page:** pick an agent for a new chat and manage agents (name, title, description, instructions, engine, model, workspace folder, approval mode, notes) from the Agents panel: edit, duplicate, pin, archive, edit an agent's notes, export an agent to a file and import one; the conversation list shows each conversation's agent. Needs a backend with the agents API; otherwise the page behaves as before. See [SETUP.md](SETUP.md#the-chat-page).

- **Desktop app, from a source checkout (experimental):** an Electron window around the local backend, started with `npm run start` in `desktop/`. It needs no `.env`: it keeps its own encryption key in the operating system's secret storage, creates and backs up its SQLite database, and only its own window can use the backend (a fresh launch token on every start). Local engines; no installer yet. Installer/platform verification remains limited; see SETUP. See [SETUP.md](SETUP.md#desktop-app-from-a-source-checkout-experimental).

- **Approval modes, saved rules and the decision log (backend):** `ask`, `accept_edits` and `plan` map onto the Claude CLI's permission modes; "always allow" saves an exact Bash command for a workspace folder, and prefix rules can be added through the API; a safety floor (recursive deletes of `/`, home or system folders, disk formatting, force pushes, fork bombs, and commands that cannot be read) is never auto-allowed; every decision is appended, redacted, to a monthly file that `GET /api/v1/decisions` reads and `GET /api/v1/decisions/export.csv` exports. Removing a saved rule is logged as `undone`. A read-only health scan (`GET /api/v1/sentinel/scan`, or `python -m app.services.sentinel`) reports retry loops, repeated denials, tool errors and failed answers without ever storing tool output. See [SETUP.md](SETUP.md#approval-modes-saved-rules-and-the-decision-log).
- **Approvals in the Chat page:** "Always allow this command" on a shell command's card (with Undo), a note when a saved rule allowed a call, the approval mode in the header, and an Approvals panel (also in desktop Settings) to manage saved rules per folder, page and filter the decision log and export it as CSV, and run the health scan. See [SETUP.md](SETUP.md#the-chat-page).

- **Engines and model selection:** Claude, Codex (`codex app-server`), a generic ACP command and OpenAI-compatible chat endpoints share durable threads. Pick an engine and model for an agent or a new chat; change an existing conversation’s model while idle. Existing conversations keep their engine when an agent changes engine. **Settings → Engines** works in the web and desktop UI, reports readiness and capabilities, and saves an ACP command or encrypted endpoint configuration. A missing Claude installation does not block another ready engine. OpenAI-compatible endpoints are chat only; agent computers require Claude. See [ENGINES.md](ENGINES.md).

- **Desktop settings:** configure the Claude executable and default workspace root with native Browse dialogs, local tools, answer/approval timeouts and output limit. Per-field saves are versioned in the database, sensitive changes are audited, and the page shows sources, effective values and validation errors. New turns use saved configuration; running turns and existing approval deadlines stay unchanged. Conversations keep their original workspace across changes and restarts. Storage information is read-only; the first-run setup can be replayed here. See [SETUP.md](SETUP.md#desktop-app-from-a-source-checkout-experimental).

- **Named agents (backend):** save instructions, engine, model, workspace and approval mode under a name and start conversations from it (`agent_id` on `POST /api/v1/threads`). Model edits apply from the next message when the conversation follows its agent and still uses that engine; approval-mode edits apply from the next message; instructions and notes are read when a conversation starts (the Claude CLI keeps a resumed session's system prompt); its workspace stays as it was when it began. Pin, archive, duplicate and delete are in `/api/v1/agents`. See [SETUP.md](SETUP.md).
- **Agent notes:** each agent keeps `MEMORY.md` in its own folder; the first 200 lines (24 KB) load into every conversation with it, with anything that looks like a secret redacted. Read and edit them with `GET`/`PUT /api/v1/agents/{id}/memory` (a hash check stops a save from overwriting the agent's own edit) or in the Agents panel; switch them off per agent; give a new agent starter notes. See [SETUP.md](SETUP.md#agent-notes-and-agent-files).
- **Topic notes, recall and compaction:** agents keep `memory/<topic>.md` notes beside `MEMORY.md` (indexed in the prompt, same redaction, atomic writes, caps and hash checks); before each turn matching note and past-conversation passages are added to the message (not the system prompt) and shown as a **Recalled** chip, with a per-agent switch; long conversations on OpenAI-compatible and ACP engines are folded into a stored excerpt summary at a per-engine token budget, marked **Earlier messages summarized**; a journal with undo and a proposed-notes queue you accept or reject. See [MEMORY.md](MEMORY.md).
- **Agent files:** export an agent as one `.agent.json` (name, title, description, instructions and optionally notes; never model, folder, approval mode or conversations) and import it elsewhere, where it starts on Ask first. See [SETUP.md](SETUP.md#agent-notes-and-agent-files).

- **Agent computers (experimental):** give an agent its own isolated Docker container and its turns run their commands and file edits there, never on this machine: non-root, no capabilities, CPU/memory/process limits, network off by default, only its workspace folder mounted. Every call still goes through the approval gate, and a one-use permit per approved call means nothing unapproved can run. Start, stop, recreate, limits, idle stop, removal and Docker health from the Agents panel or `/api/v1/computers`; a Computer chip in the chat header. See [COMPUTERS.md](COMPUTERS.md).

- **Desktop first-run setup:** detects engine readiness and explains CLI sign-in, selects an engine/model and workspace root, explains approval modes and optionally creates a starter agent. Completion is saved in the app database; skip and replay are available. CLI source prerequisite diagnostics are available with `npm run doctor` in `desktop/`. Source desktop engine/setup flows have been exercised on macOS; signed installers, updates and Linux first-run verification remain open.

Limitations: see "Known limitations" in the [README](../README.md).
