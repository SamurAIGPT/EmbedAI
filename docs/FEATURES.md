# Features

Shipped capabilities. Planned work is in [ROADMAP.md](ROADMAP.md).

- Run Claude Code tasks in disposable Boat sandboxes from Telegram or the web UI.
- Connect Claude through its OAuth login flow; optionally connect GitHub.
- Approval prompts for risky actions (file writes, shell commands, Git pushes) with remembered permission rules and a Git command classifier.
- Continue completed tasks in the same Claude conversation from the web UI.
- Schedule recurring prompts with failure tracking; results reported to Telegram-linked users.
- Encrypted credential storage; sandbox, task, permission and schedule records in PostgreSQL (default), or in a local SQLite file when `DATABASE_BACKEND=sqlite` (experimental; see [SETUP.md](SETUP.md#database)).
- Guest web mode without Telegram, optionally linked to a Telegram identity via link codes.

- **Local Claude (experimental, off by default):** run a prompt through your own signed-in `claude` CLI on the same machine, from the web UI, with the answer appearing as Claude writes it. Chat-only by default. With `LOCAL_TOOLS_ENABLED=true` Claude can read and write files in its workspace folder and run commands, shown as a timeline, and each call it would ask about waits for your Allow or Deny in the page. Only usable from the machine running the backend. See [SETUP.md](SETUP.md#local-claude-experimental).

- **Durable threads and the Chat page (experimental, off by default):** with the same switch as local Claude (`LOCAL_EXECUTION_ENABLED`), conversations are stored in the database. Messages, answers, tool calls and approvals survive a page refresh and a backend restart, and each message continues the same Claude session. A server-sent-events stream shows answers as they are written and resumes exactly after a disconnect. An interrupted turn is marked and never run again; a lost Claude session must be reset explicitly. The Chat page (`/chat`, linked from the home page) shows them: a list of conversations, answers as they are written, tool calls and approvals in order, and a clear message with a way forward when a session is lost. You can stop an answer, and rename, archive or delete a conversation. Answers are formatted as Markdown (code blocks have a Copy button; raw HTML is never rendered). Not yet: search. See [SETUP.md](SETUP.md#the-chat-page).

- **Agents in the Chat page:** pick an agent for a new chat and manage agents (name, title, description, instructions, model, workspace folder, approval mode, notes) from the Agents panel: edit, duplicate, pin, archive, edit an agent's notes, export an agent to a file and import one; the conversation list shows each conversation's agent. Needs a backend with the agents API; otherwise the page behaves as before. See [SETUP.md](SETUP.md#the-chat-page).

- **Desktop app, from a source checkout (experimental):** an Electron window around the local backend, started with `npm run start` in `desktop/`. It needs no `.env`: it keeps its own encryption key in the operating system's secret storage, creates and backs up its SQLite database, and only its own window can use the backend (a fresh launch token on every start). Local Claude only; no installer yet. Verified on Windows only. See [SETUP.md](SETUP.md#desktop-app-from-a-source-checkout-experimental).

- **Approval modes, saved rules and the decision log (backend):** `ask`, `accept_edits` and `plan` map onto the Claude CLI's permission modes; "always allow" saves an exact Bash command for a workspace folder, and prefix rules can be added through the API; a safety floor (recursive deletes of `/`, home or system folders, disk formatting, force pushes, fork bombs, and commands that cannot be read) is never auto-allowed; every decision is appended, redacted, to a monthly file that `GET /api/v1/decisions` reads and `GET /api/v1/decisions/export.csv` exports. Removing a saved rule is logged as `undone`. A read-only health scan (`GET /api/v1/sentinel/scan`, or `python -m app.services.sentinel`) reports retry loops, repeated denials, tool errors and failed answers without ever storing tool output. See [SETUP.md](SETUP.md#approval-modes-saved-rules-and-the-decision-log).
- **Approvals in the Chat page:** "Always allow this command" on a shell command's card (with Undo), a note when a saved rule allowed a call, the approval mode in the header, and an Approvals panel (also in desktop Settings) to manage saved rules per folder, page and filter the decision log and export it as CSV, and run the health scan. See [SETUP.md](SETUP.md#the-chat-page).

- **Desktop settings:** configure the Claude executable and default workspace root with native Browse dialogs, local tools, answer/approval timeouts and output limit. Per-field saves are versioned in the database, sensitive changes are audited, and the page shows sources, effective values and validation errors. New turns use saved configuration; running turns and existing approval deadlines stay unchanged. Conversations keep their original workspace across changes and restarts. Storage information is read-only; no onboarding wizard yet. See [SETUP.md](SETUP.md#desktop-app-from-a-source-checkout-experimental).

- **Named agents (backend):** save instructions, model, workspace and approval mode under a name and start conversations from it (`agent_id` on `POST /api/v1/threads`). Model and approval-mode edits apply from a conversation's next message; instructions and notes are read when a conversation starts (the Claude CLI keeps a resumed session's system prompt); its workspace stays as it was when it began. Pin, archive, duplicate and delete are in `/api/v1/agents`. See [SETUP.md](SETUP.md).
- **Agent notes:** each agent keeps `MEMORY.md` in its own folder; the first 200 lines (24 KB) load into every conversation with it, with anything that looks like a secret redacted. Read and edit them with `GET`/`PUT /api/v1/agents/{id}/memory` (a hash check stops a save from overwriting the agent's own edit) or in the Agents panel; switch them off per agent; give a new agent starter notes. See [SETUP.md](SETUP.md#agent-notes-and-agent-files).
- **Agent files:** export an agent as one `.agent.json` (name, title, description, instructions and optionally notes; never model, folder, approval mode or conversations) and import it elsewhere, where it starts on Ask first. See [SETUP.md](SETUP.md#agent-notes-and-agent-files).

- **Agent computers (experimental):** give an agent its own isolated Docker container and its turns run their commands and file edits there, never on this machine: non-root, no capabilities, CPU/memory/process limits, network off by default, only its workspace folder mounted. Every call still goes through the approval gate, and a one-use permit per approved call means nothing unapproved can run. Start, stop, recreate, limits, idle stop, removal and Docker health from the Agents panel or `/api/v1/computers`; a Computer chip in the chat header. See [COMPUTERS.md](COMPUTERS.md).

Limitations: see "Known limitations" in the [README](../README.md).
